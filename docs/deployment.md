# Configuration and deployment

## Environment variables

Every variable is validated at startup of the area that needs it (`src/config/env.ts`), so a missing PayPal key doesn't stop an AI-only script and the reverse.

| Variable | Required | Purpose |
|---|---|---|
| `PAYPAL_ENV` | no, default `sandbox` | `sandbox` or `live`. Sandbox keys are rejected with a 401 when this says `live` |
| `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET` | yes | The PayPal REST app that acts as the platform |
| `PAYPAL_WEBHOOK_ID` | for webhooks | The webhook whose signatures are verified. Get it from `npm run paypal:webhook -- <public url>` |
| `AI_PROVIDER` | no, default `google` | `google` (Gemini) or `anthropic` (Claude) |
| `AI_MODEL` | recommended | Model id for that provider. **Set it explicitly**: the built-in default is a moving alias that can be overloaded. The demo uses `gemini-flash-lite-latest` |
| `GOOGLE_GENERATIVE_AI_API_KEY` / `ANTHROPIC_API_KEY` | one of them | Key for the chosen provider |
| `GITHUB_TOKEN` | no | Raises the GitHub rate limit. Delivered work must be a pull request on a **public** repository |
| `DATABASE_URL` | yes | Postgres connection string |
| `APP_BASE_URL` | no | Public URL of the app; PayPal redirects back to it. Falls back to Render's `RENDER_EXTERNAL_URL`, then `http://localhost:3000` |
| `AUTH_SECRET` | in production | 32+ characters. Keys invite links and sign-up IP hashes. Changing it invalidates existing invite links |
| `ADMIN_EMAILS` | for an admin | Comma-separated emails that get the admin role, checked on every request |
| `DEMO_ADMIN_PASSWORD` | for the seed | Password `npm run seed:demo` sets for `admin@demo.dev`, which must also be in `ADMIN_EMAILS` |
| `JOBS_PER_DAY`, `SIGNUPS_PER_IP_PER_HOUR` | no, defaults 5 and 3 | Abuse limits for a public deployment; each job costs AI calls |

`.env.example` lists the same keys for local use. `.env` is gitignored.

## Deploying to Render

`render.yaml` is a Render Blueprint: one Node web service and one Postgres database.

1. **Create the Blueprint.** In Render: New → Blueprint, pick this repository. Render asks for the secrets marked `sync: false` and generates `AUTH_SECRET`.
2. **Add what the Blueprint doesn't carry.** `JOBS_PER_DAY` and `SIGNUPS_PER_IP_PER_HOUR` if you want other limits than the defaults.
3. **Let the first deploy finish.** The pre-deploy command runs `npm run db:migrate`. Check `https://<your-service>/api/health` returns 200.
4. **Register the webhook.** Locally, with the same PayPal credentials: `npm run paypal:webhook -- https://<your-service>`. Put the printed id in `PAYPAL_WEBHOOK_ID` on Render.
5. **Seed the admin.** In the service's **Shell** tab: `npm run seed:demo`. It prints `ready admin@demo.dev`.

Saving an environment change redeploys the service. Pushing to `main` deploys too.

### Values that must differ from a local `.env`

| Variable | On Render |
|---|---|
| `DATABASE_URL` | Filled in by the Blueprint from the Render database. Don't paste the local one |
| `APP_BASE_URL` | Leave unset, or set it to the public `https://…onrender.com` address |
| `AUTH_SECRET` | Generated by Render. Don't overwrite it |
| `PAYPAL_WEBHOOK_ID` | The id of the webhook registered for the Render URL, not a tunnel URL |

### Problems we hit, and their causes

| Symptom | Cause | Fix |
|---|---|---|
| Deploy error "unable to access your GitHub repository" | The repository was renamed after the service was created | Settings → Build → Source: reconnect the service to the current repository |
| "The AI couldn't draft the criteria" on every job | `AI_MODEL` was missing, so the app used the default alias, which was overloaded | Set `AI_MODEL` explicitly |
| "PayPal API 401 AUTH_FAILED" when funding | Client id and secret didn't form a valid pair (a paste error) | Re-paste both; confirm `PAYPAL_ENV=sandbox` |
| Disputes never arrive on their own | `PAYPAL_WEBHOOK_ID` doesn't match the webhook registered for this URL, or the service was suspended | Fix the id; use **Sync from PayPal** on the disputes page to recover missed ones |

### Choosing a model

`npm run spike:models` makes a few small calls to every Gemini model the key can reach and prints the success rate and latency. Free-tier keys have low per-model quotas and occasional "high demand" errors, so run it shortly before a demo. The app degrades cleanly when the provider fails: job creation shows a message and creates nothing, and a failed verification offers **Retry verification** and, for admins, **Review it manually**.

## Removing demo data

The app has no delete action. To remove jobs from a deployment, list them and delete by id from the service shell:

```bash
node -e 'const sql=require("postgres")(process.env.DATABASE_URL);sql.unsafe("select id,title,status,amount_minor/100 as amount from jobs order by created_at").then(r=>{console.table(r);return sql.end()})'

node -e 'const sql=require("postgres")(process.env.DATABASE_URL);(async()=>{for(const id of process.argv.slice(1)){await sql.unsafe("delete from events where job_id=$1",[id]);const r=await sql.unsafe("delete from jobs where id=$1 returning title",[id]);console.log(r.length?"deleted: "+r[0].title:"not found: "+id)}await sql.end()})()' <id> <id>
```

This is permanent and only cleans ProofPay's database; PayPal keeps its own records. A PayPal dispute is matched to a job by its capture, so deleting a paid job leaves any later dispute on it without history.
